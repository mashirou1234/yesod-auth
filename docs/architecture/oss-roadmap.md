# YESOD Auth OSS 改修計画

決定日: 2026-10-23 JST。対象: 個人開発者、小規模チーム、社内の複数アプリ運用者。
プロダクトの目的は、シンプルな構成で、認証の導入・接続確認・運用を画面から進められるようにすること。

追跡: [#798](https://github.com/mashirou1234/yesod-auth/issues/798)、[M0 マイルストーン](https://github.com/mashirou1234/yesod-auth/milestone/1)。

## 決定した制約

- 正式リリース前のため、旧 API・設定・管理画面の互換維持、移行期間、互換レイヤーを要求しない。
- 不要な契約は変更・削除できる。変更内容と現行の起動手順を文書化し、同梱サンプルとテストを同時に更新する。
- この方針は実データの削除、既存作業の破棄、認証情報の公開、本番変更を許可するものではない。
- FastAPI、PostgreSQL、Valkey と既存 OAuth 接続を活かす。初期段階でサービス分割を増やさない。
- 初期対象は一つの運営主体が管理するセルフホスト。複数の無関係な組織を同居させる SaaS は対象外。

## 設計の軸

1. 初回は既定プロジェクトを一つ作り、最初のアプリの登録を案内する。必要になるまで組織階層や詳細設定を表示しない。
2. プロジェクトをユーザー・接続設定の境界、アプリを client / redirect / audience の境界にする。同じプロジェクトのアプリでもトークンの利用先は分離する。
3. 外部 OAuth/OIDC への接続と、利用アプリに対する OIDC 提供を分ける。OIDC 対応を独自 JWT 発行と同一視しない。
4. GUI と将来の CLI は同じ管理 API を使う。管理画面は DB を直接更新しない構成へ段階的に置換する。
5. 設定の入力・検証・有効化を分け、検証の対象となった設定の版を記録する。変更後の古い成功結果を流用しない。
6. GUI 管理の秘密情報は暗号化し、鍵は DB 外で管理する。環境変数・Secrets 管理の値には管理元を表示し、GUI から上書きしない。
7. 外部サービスでのアプリ登録、同意、審査は手動の境界として案内し、中断・再開を可能にする。
8. 新コンソールは小さな試作でフォーム、アクセシビリティ、配布・保守負荷を確認して技術選定する。

## 優先順位

| 区分 | 内容 | 理由 |
|---|---|---|
| Must | 安全条件、実効 CI、アプリ登録、設定案内、実接続確認、OIDC 接続、配布と運用手順 | 導入から継続利用を成立させる |
| Should | 管理者・運用者・閲覧者の役割、汎用 upstream OIDC、秘密値を除く設定 export | 社内利用・再現可能な運用を広げる |
| Could | SDK、テーマ、新規 provider | 標準接続と最初の成功経路が安定してから拡張する |
| 対象外 | SAML/SCIM、複雑な認可エンジン、マネージド SaaS、認証方式の一括追加 | 初期の運用・復旧範囲を限定する |

## マイルストーン

| 段階 | 成果 | 終了条件 |
|---|---|---|
| M0 基盤整備・仕様確定 | CI、設定の安全条件、管理者セッション修正、アプリ登録からログインまでの仕様 | 回帰テスト・CI 定義・仕様・Issue 対応表が揃う。本番利用可能の宣言は含まない |
| M1 認証境界・管理 API | プロジェクトとアプリ、管理権限、コード交換、秘密情報管理 | URL に token を出さず、アプリ間・権限間の負例を拒否できる |
| M2 初回導入 | 起動から一つの実 OAuth とサンプルアプリまでのウィザード | 初見の利用者が設定、再開、失敗修正、ログインを完了できる |
| M3 標準接続・複数アプリ | OIDC の合意済み subset、鍵更新、複数アプリ、既存 provider の回帰確認 | 二つの独立した client で認証し、誤った audience / redirect / code を拒否できる |
| M4 運用・OSS 公開準備 | 診断、監査、セッション管理、配布物、貢献・脆弱性窓口 | 新規導入、更新、バックアップ・復旧を配布物で再現できる |

M0 の今回の実装対象は、実構成を検証する CI、runtime mode と本番 credential 検証、JWT issuer/audience、管理者 URL session 撤去と絶対期限。
アプリ登録・OIDC・認可コード交換は今回仕様を確定し、M1 以降で実装する。
M0 を終えても、#680 の token query redirect、#681/#682 の refresh rotation/reuse、#683 の外部 token 保存、#694 の管理者 login 制限などは公開前の残課題である。

## 最初の受入条件

- PR / push で Python の lint、API と admin のテスト、必要な build が実行される。Rust ファイル不在による成功を品質証拠にしない。
- 自動承認だけで認証変更が採用されない。必須 CI の成功とレビューの運用を分けて確認する。
- runtime mode の不明値を拒否し、本番で既知・弱い鍵や管理者 password、mock/debug 認証を許可しない。
- JWT は署名だけでなく期待する issuer/audience を検証する。M0 の audience はインスタンス設定であり、アプリ別分離の実装済み表示はしない。
- URL の session を管理者認証に使わず、状態が不正・期限切れなら再認証する。logout 後に状態を再利用できない。
- [アプリ登録からログインまでの仕様](app-registration-login-spec.md) の正常系・異常系を次の実装の契約にする。
- 意図した仕様変更で失敗する Red と、修正後の Green を記録する。

## 検証と公開条件

単体・境界テスト、実 PostgreSQL/Valkey による統合検証、実ブラウザによる操作、公開候補の実 OAuth 接続を分けて記録する。
ブラウザ表示だけで完了扱いにせず、console、server、型検査/build の関連ログを確認する。
秘密値の漏出、別アプリへの token 流用、認可コード再利用、管理者の権限逸脱、失効と並行操作を負例として扱う。
セキュリティ上の残課題がある状態を、production-ready や stable release と表示しない。

## 進め方と成果指標

2 週間単位で利用者が新しくできることを一つ届ける。初期は CI と安全条件を優先し、その後の配分案は体験 60%、安全性・契約 25%、配布・文書・コミュニティ 15%。
日程は担当者の確定と最初の期間の実績から見積もり、Issue 件数だけを速度指標にしない。

初期目標は、環境準備後 10 分以内の模擬ログイン、外部資格情報取得後 15 分以内の実接続、初見の協力者 5 名中 4 名の口頭支援なし完遂。
外部審査時間は別計測。目標値は未測定であり、利用者テストで再評価する。
既存 Issue の採否は [対応表](oss-issue-map.md) に記録する。重複による統合と実装完了による close を区別する。
